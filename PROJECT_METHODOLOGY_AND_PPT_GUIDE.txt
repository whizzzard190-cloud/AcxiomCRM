1. EXECUTIVE SUMMARY & PROBLEM STATEMENT
--------------------------------------------------------------------------------
Most legacy CRM applications suffer from significant architectural deficiencies:
- Weak authorization: Relying on scattered "if" statements in UI controllers that
  allow horizontal privilege escalation (Insecure Direct Object References - IDOR).
- Fragile data integrity: Unvalidated stage transitions, missing duplicate detection,
  and uncoordinated multi-step mutations that leave orphan records.
- Inadequate auditability: Mutation or deletion of logs, exposure of user passwords
  in logs or APIs, and lack of compliance traceability.
- Over-engineering: Bloating projects with external frameworks (CQRS, MediatR,
  Tailwind, node_modules) when standard built-in framework capabilities are superior.

AcxiomCRM was built to solve these enterprise challenges. It is a secure, role-aware,
auditable, and strictly validated workflow CRM built entirely with C# and ASP.NET Core 10.
It strictly adheres to clean architectural principles, defense-in-depth security, and
zero-trust resource scoping.


2. ARCHITECTURAL PATTERN & LAYERED DESIGN METHODOLOGY
--------------------------------------------------------------------------------
AcxiomCRM follows a strict 4-Tier Layered Architecture:

[Presentation Layer] -> Razor MVC Controllers & REST API Controllers (Controllers/Api)
         |
[Domain Service Layer] -> Business logic, state machines, workflow rules, scoping
         |
[Cross-Cutting Layer] -> Security authorization, append-only auditing, rate limiting
         |
[Persistence & Data]  -> Entity Framework Core 9.0 DbContext & SQL Server Database

Key Architectural Decisions:
1. No Entity Leakage: Internal database entities (Customer, Lead, Opportunity) are
   strictly barred from crossing the API boundary. The REST API exposes only
   strongly-typed Data Transfer Objects (DTOs) from `DTOs/ApiDtos.cs`. This prevents
   mass assignment attacks, over-posting, and accidental data disclosure.
2. Built-in Framework Primitives over External Bloat: Instead of adding 15 NuGet
   packages and npm dependencies, AcxiomCRM harnesses ASP.NET Core native features:
   - Built-in Identity for password hashing, lockout, and session cookies.
   - Built-in RateLimiter (`FixedWindowLimiter`) for authentication brute-force protection.
   - Built-in `IValidatableObject` and DataAnnotations for cross-property validation.
   - Bootstrap 5 and Chart.js delivered via trusted CDNs. Zero npm/node overhead.
3. Centralized Services: All business rules reside in dedicated domain services
   (CustomerService, LeadService, OpportunityService, FollowUpService, ActivityService,
   DashboardService, ReportService, AuditService, ResourceAuthorizationService).
   Controllers remain thin, orchestrating HTTP inputs and redirecting to views or
   returning typed ProblemDetails/JSON results.


3. SECURITY & ZERO-TRUST SCOPING METHODOLOGY
--------------------------------------------------------------------------------
AcxiomCRM implements a comprehensive Zero-Trust security model:

A. Centralized Role & Hierarchical Scope Authorization:
   The system defines three core roles: Admin, Manager, and SalesExecutive.
   Instead of ad-hoc checks in controllers, all record queries and mutations pass
   through `IResourceAuthorizationService`:
   - Admin: Has global visibility across all organizational units.
   - Manager: Governed by the managerial reporting tree (`ManagerId` foreign key
     on `ApplicationUser`). A manager can view and manage records owned by themselves
     and by Sales Executives who report directly to them. Records belonging to
     executives reporting to other managers are strictly inaccessible.
   - SalesExecutive: Strict ownership isolation. An executive can ONLY view, edit,
     or mutate records where `OwnerId == currentUserId` or `AssignedTo == currentUserId`.
   Attempts by an executive to tamper with query strings, route IDs, or POST bodies
   to view or edit another executive's customer or deal are intercepted and denied.

B. Identity, Password Policy & Lockout Defense:
   - Password Hashing: PBKDF2 with HMAC-SHA256 via ASP.NET Core Identity.
   - Password Rules: Minimum 8 characters, requiring uppercase, lowercase, digit,
     and special character.
   - Brute Force Lockout: Automatically locks an account after 5 consecutive failed
     login attempts for 15 minutes.
   - Administrative Unlock: Only Admins can manually release locked accounts,
     and the unlock action is permanently audited.

C. Web Defense-in-Depth:
   - CSRF Immunity: `[ValidateAntiForgeryToken]` is enforced across all state-changing
     MVC POST actions. Anti-forgery cookies are configured with `SameSite=Strict`.
   - Cookie Hardening: All application cookies enforce `HttpOnly=true`,
     `SameSite=Strict`, and `SecurePolicy=Always`.
   - SQL Injection Immunity: 100% EF Core parameterized LINQ queries. Zero raw SQL
     string concatenation exists anywhere in the repository.
   - Security Headers: Custom middleware injects `X-Content-Type-Options: nosniff`,
     `X-Frame-Options: SAMEORIGIN`, and `Referrer-Policy: strict-origin-when-cross-origin`.
   - HSTS: HTTP Strict Transport Security is active with 1-year max age and subdomains.
   - Rate Limiting: FixedWindow rate limiter permits a maximum of 5 requests per
     minute on `/api/auth/*` endpoints.


4. CORE BUSINESS WORKFLOW ENGINES
--------------------------------------------------------------------------------
A. Customer Management & Duplicate Guard:
   - Strict validation: Required CustomerName, 10-digit Indian phone starting with
     6-9 (`^[6-9]\d{9}$`), and valid RFC email format.
   - Duplicate Detection: Real-time case-insensitive, whitespace-trimmed duplicate
     detection on both Email and Phone. Attempts to create or update a customer
     with an existing email or phone are rejected (HTTP 409 Conflict in API,
     ModelState validation error in MVC).
   - Soft Deactivation: Customers can be deactivated (`Status = "Inactive"`) rather
     than hard-deleted, maintaining historical integrity.

B. Lead Lifecycle & State Machine:
   - Allowed Statuses: `New`, `Contacted`, `Qualified`, `Unqualified`, `Converted`, `Lost`.
   - Valid Transitions:
     - New -> Contacted | Lost
     - Contacted -> Qualified | Unqualified | Lost
     - Qualified -> Converted | Lost
     - Unqualified -> Contacted | Lost
     - Converted & Lost are terminal states.
   - Invalid status jumps (e.g., New directly to Converted) are rejected.
   - Open Leads metric dynamically includes New, Contacted, Qualified, and Unqualified,
     excluding terminal states.

C. Atomic Lead Conversion Workflow:
   - Conversion is restricted to `Qualified` leads.
   - Executed within an ACID transaction (`BeginTransactionAsync`):
     1. Creates a new Customer record (or links existing duplicate).
     2. Optionally creates a new Opportunity linked to the customer.
     3. Updates Lead status to `Converted`, storing `ConvertedCustomerId` and
        `ConvertedOpportunityId`.
     4. Emits a comprehensive audit entry detailing the conversion linkage.
   - If any step fails, the entire transaction rolls back, preventing partial data corruption.

D. Opportunity Pipeline & Revenue Forecasting:
   - Business Invariants: Amount must be > 0. Probability must be 0 to 100.
     ExpectedCloseDate cannot be in the past for active deals.
   - Stages: `Qualification` -> `Proposal` -> `Negotiation` -> `Won` | `Lost`.
   - Interactive Kanban Pipeline view organizes open deals by stage.
   - Weighted Pipeline Value calculation: `Amount * Probability / 100`, providing
     accurate sales forecasting for managers and executives.

E. Follow-Up Engine & Overdue Tracking:
   - Polymorphic association: Can be linked to a Customer, Lead, or Opportunity
     (at least one association is required).
   - Past-Date Protection: Follow-ups cannot be scheduled or rescheduled into the
     past for planned items.
   - Overdue Detection: Calculated dynamically (`FollowUpDate < Today && Status == "Planned"`).
   - Complete & Reschedule Workflows: Audit logs capture completion remarks and
     reschedule history with timestamps.

F. Activity Journaling:
   - Captures Calls, Meetings, Emails, and Tasks linked to customers or leads,
     providing a chronological timeline of all client touchpoints.


5. AUDITING & COMPLIANCE METHODOLOGY
--------------------------------------------------------------------------------
- Append-Only Architecture: The `AuditLog` table and `IAuditService` expose zero
  Update or Delete methods. Once written, audit records are permanent and immutable.
- Recursive Sensitive Property Stripping: Before persisting `OldValue` and `NewValue`
  JSON payloads, `AuditService.SanitizeAndSerialize()` traverses the JSON hierarchy
  and recursively strips `Password`, `PasswordHash`, `Token`, `Secret`,
  `SecurityStamp`, and `ConcurrencyStamp`. Passwords are NEVER written to logs or DB.
- Comprehensive Coverage: Audits every authentication event (Login, Failure, Lockout,
  Unlock, Logout), CRUD operations on all entities, role modifications, lead conversions,
  and follow-up status changes.


6. REPORTING & ANALYTICAL ENGINE
--------------------------------------------------------------------------------
- 8 Distinct Analytical Reports:
  1. Customer Directory Report (by status, city, owner)
  2. Lead Pipeline Report (by source, priority, status)
  3. Follow-Up Schedule Report (by type, status, overdue status)
  4. Opportunity Pipeline Report (by stage, expected close date)
  5. Pipeline Revenue & Forecasting Report (stage-wise & owner-wise weighted sums)
  6. Lead Conversion Performance Report (conversion rates & velocity)
  7. User & Team Activity Report (activity volume by rep)
  8. Compliance Audit Trail Report (filterable by user, module, action, date range)
- Role Scoping: Sales executives view only their own operational reports; managers
  view their team; admins view global data.
- Streaming CSV Export: Generates RFC 4180 compliant CSV files directly to the
  HTTP response stream with zero memory buffering.
